# Zero-Cost Self-Hosted Runner Setup

Use this setup for private repositories that must not consume GitHub-hosted Actions minutes.

## Standard labels

All private repositories using `platform-ci` target:

```yaml
runs-on: [self-hosted, Linux, X64]
```

GitHub assigns `self-hosted`, OS, and architecture labels automatically when a standard Linux x64 runner is registered.

## Current topology

For user-owned repositories, register the same physical Linux machine separately with each repository:

- `dporkka/adacavo`
- `dporkka/apex`
- `dporkka/nulang-cloud`

Use separate install directories and runner services:

```text
~/actions-runners/
├── adacavo/
├── apex/
└── nulang-cloud/
```

One physical machine is sufficient. Each registration gives GitHub a repository-scoped runner endpoint.

## Registration

Repeat these steps for each private repository.

1. Open the repository on GitHub.
2. Go to **Settings → Actions → Runners**.
3. Select **New self-hosted runner → Linux → x64**.
4. Create the repository-specific directory, for example:

   ```bash
   mkdir -p ~/actions-runners/adacavo
   cd ~/actions-runners/adacavo
   ```

5. Run the download, extraction, and `./config.sh` commands GitHub displays. Registration tokens are short-lived; use the commands generated by GitHub rather than storing a token in this repository.
6. Give each runner a clear name such as `t14-adacavo`, `t14-apex`, or `t14-nulang-cloud`.
7. Verify GitHub shows the default labels `self-hosted`, `Linux`, and `X64`.
8. Install and start it as a service:

   ```bash
   sudo ./svc.sh install
   sudo ./svc.sh start
   sudo ./svc.sh status
   ```

Repeat from a separate directory for the other repositories.

## Host prerequisites

The shared workload currently assumes the host can provide:

- Git and curl
- Docker Engine with the runner user able to use Docker
- `sudo` for package installation
- enough disk for Docker/Playwright/Rust build caches
- outbound HTTPS to GitHub and the services under test

Language toolchains are installed by workflows when practical. Adacavo additionally uses Docker service containers, Playwright/Chromium, PostgreSQL client tools, and container image builds.

Recommended baseline for the host:

```bash
sudo usermod -aG docker "$USER"
docker version
git --version
curl --version
```

Log out/in after changing Docker group membership.

## Capacity policy

A GitHub self-hosted runner process executes one job at a time, but three repository registrations on one physical machine can still receive three jobs concurrently. Start conservatively:

- keep workflow `cancel-in-progress: true` where safe
- keep matrix `max-parallel: 1` on expensive build matrices
- avoid running redundant workflows through affected-path gating
- monitor RAM, swap, disk, Docker cache, and CPU during the first few runs

If the host becomes saturated, stop one or more repository runner services while heavy validation is running, or move the repositories into an organization and use one organization-level runner.

## Better long-term topology

An organization-level self-hosted runner can process jobs for multiple repositories in that organization. If Adacavo, Apex, and Nulang Cloud are later moved into a GitHub organization, replace the three repository registrations with one organization runner or runner group and grant it access only to the private repositories that need CI.

Do **not** put untrusted public-fork pull requests on a self-hosted runner. Public repositories such as `nulang-org/nulang` should continue using GitHub-hosted runners unless you establish a hardened, isolated runner model.

## Zero-cost policy

Private callers should include:

```yaml
jobs:
  runner-policy:
    uses: dporkka/platform-ci/.github/workflows/reusable-runner-policy.yml@v1
    with:
      runner_json: '["self-hosted","Linux","X64"]'
```

The policy rejects direct GitHub-hosted labels such as `ubuntu-latest`, `windows-latest`, and `macos-latest` from `.github/workflows`.

## What remains free vs external

Self-hosting removes GitHub-hosted runner compute from private CI. It does not make third-party services free. Workflows invoking services such as EAS, Vercel, Cloud Run, Neon, R2, or external scanners can still be subject to those providers' own plans and quotas. Keep expensive deployments manual or path-gated where appropriate.
